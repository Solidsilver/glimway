# Verified step-back review after 0.9

## Summary

Shared camp fights now have the right foundations: one server outcome, epoch/cycle-bound
claims, shared combat numbers, and client observation that continues under menus. The
earlier read-ordering and worker-buffer fixes are present. This does not need another
architecture round before friends can play together.

The most useful next work is making camp rewards recover reliably, keeping cooldowns
readable with reduced motion, and stopping enemy colliders from accumulating. The
server also retains fight geometry beyond its useful lifetime. CI passes are less
reassuring than they look: the reviewed commit passed with three full-suite retry
passes, and fight changes do not select the dedicated fight specs locally.

Some reviewer explanations were wrong. Kindle deliberately sends the patch's position,
two tiles ahead; moving it to the caster's feet would break the ability. The
remember/forget failure is after reload, not immediately after disconnect. Focus
escapes cannot safely be dismissed as test sampling noise. Those distinctions matter
more than increasing timeouts. Large Link/UI extractions and stale prose can follow
the concrete fixes.

Snapshot: `268c9b42e18f1b7f9bdd7ef82a01cd1ac5c513c6`. All citations below are to this
worktree unless explicitly identified as CI history. `S`, `G`, `U`, and `T` identify
the numbered findings in the server, game, UI, and tooling reports respectively.
Priorities: P1 affects ordinary player use; P2 is a correctness or maintenance risk;
P3 is cleanup. Size S is a focused patch; M is several small patches with boundary tests.
Confirmed means the stated mechanism is supported by code or a probe, not that its
frequency has been measured in production.

## Confirmed findings

### Player-facing recovery and feedback

**C1 — P1: Camp reward recovery stops after four reads; a separate server handoff race
can preserve an early refusal. [G1; S1 is the P2 server part]**

`src/game/wilds/camp-fights.ts:32` and `:67` cap recovery at four requests while the room
continues showing a completed fight. A terminal-only probe of the real class made
exactly four requests at 0, 1.5, 3 and 4.5 seconds, then none through 120 seconds.
`src/game/wilds/entities.ts:479`, `:524` and `:731` require the near read's claim word
both to offer and to execute the interaction. `server/internal/api/wilds.go:521`
reads durable witnesses, so a fall committed after the budget can leave a stationary
player without a claim prompt until another refresh. The probe establishes the
cutoff; it does not establish that multi-second fall writes are common.

Separately, `server/internal/fights/actor.go:308` and `:313` answer attacks/casts and
emit their events without draining falls; draining normally waits for `:357`, with
exit protection at `:255`. `server/internal/api/fall_writer.go:189` waits only for
already-enqueued falls and returns immediately if there are none (`:199`). A claim
in this inter-tick gap can get `not-defeated` (`wilds.go:495`), which is terminal for
that key (`op_idempotency.go:315`, `op.go:168`). This is confirmed by the exact ordering,
not an end-to-end reproduction. The present UI refreshes and requires the stored
word before claiming, so the server race alone is not evidence that a normal E press
regularly fails. A new action uses a fresh key (`entities.ts:534`).

Fix: client lane S, retain slower, spaced recovery while the same unclaimed cycle is
complete, with lifecycle cancellation and one in-flight read. Keep durable eligibility
as prompt authority; do not grant eligibility from corpses. Server lane S–M, hand off
falls on every damage path, including settlement, before publishing completion or
answering its result. Merely adding a drain after an already-sent result leaves a
smaller race. Explicitly decide whether bounded-wait `not-defeated` should be replayable
as a transient refusal. Guard delayed commits beyond 4.5 seconds, same-tick completion,
settled bolts, exact-key retries and room exit. These are coordinated subpatches, not
duplicate findings.

**C2 — P1: Reduced motion hides cooldown progress. [U1]**

`src/app.css:605` forces all animation durations to `1ms !important`; the real-duration
ability and roll sweeps at `src/ui/Hud.svelte:362` and `:422` are non-important inline
styles. The sweep reaches its transparent end (`:1231`, `:1251`) almost immediately
while the ability remains on cooldown. The same snippet also serves touch controls.
The CSS cascade confirms the defect; no visual run was performed.

Fix: UI lane S, provide a static remaining-time readout under reduced motion, or
explicitly preserve the single cooldown progress animation while suppressing decorative
loops. Guard ability and roll timing with reduced motion on desktop and touch.

**C3 — P2: Valid claim/relight refusals get transport-failure copy. [U2]**

`src/game/wilds/entities.ts:78` omits `already-lit`, `lantern-not-found`,
`beyond-frontier`, `entity-not-found` and other endpoint/shared refusal codes;
`:564` sends them to “The Wilds didn't answer.” A double relight reaches the real
`already-lit` branch (`server/internal/api/wilds.go:590`); it is not a network failure.
The report's claim that some lantern codes were already in this table is incorrect.

Fix: UI lane S, move this wording into the domain copy module and cover reachable
claim/relight codes, including epoch/access errors. Distinguish malformed requests from
ordinary unavailable targets. Add a focused mapping check and a double-relight assertion.

### Fight correctness and resource lifetime

**C4 — P2: Fight-location caches lack eviction and retain obsolete ground. [S2]**

`server/internal/api/presence_fights.go:404` caches every loaded location's geometry,
including campless locations (`:406`, `:472`). The only deletion is lazy epoch expiry
when that location is covered again (`:295`); `fightClosed` removes rooms, not locations
(`:215`). Non-expiring Tangle entries remain across room sleep. Expired outer entries
can also remain if nobody revisits them. This grows across worlds/visited locations,
even though today's per-world frontier limits its initial scale.

Geometry is captured from effective ground at `:477` and reused by `fightGround` at
`:727`. Path mutations have no fight-cache invalidation (`open_map_paths.go:153`).
Correction to the example: laying stone requires an already-walkable tile (`:247`);
**clearing a blocking tile** demonstrates the walkability mismatch
(`server/internal/chunks/effective.go:59`). Rooms intentionally retain wake-time
geometry; perpetual reuse in campless chunks is the additional bug.

Fix: server lane M, bound both caches and invalidate changed chunks after a successful
ground transaction. Preserve active room identity and the chosen wake-time room geometry;
refresh campless ground and subsequent wakes. Define the lifetime of active shared
ground explicitly rather than accidentally mixing old room and refreshed cache copies.
Guard many worlds/locations, room sleep/revisit, expiry without revisit and a cleared
campless tile crossed by a dash/bolt.

**C5 — P2: Tool damage remains client-selected. [S3]**

`server/internal/api/presence_fights.go:602` checks the tool flag only to permit mage
slashes; `server/internal/fights/room.go:956` passes it into server damage unchanged.
`server/internal/rules/fight_math.go:44` applies the tool fraction. A warrior/rogue
client can label the same slash non-tool and receive full damage. This is a confirmed
authority gap, not evidence of an honest-client damage mismatch or current cheating.

Fix: server lane M only after choosing the small protocol contract: carry and validate
an explicit held mode, or document held mode as trusted under the friends model. Pack
ownership alone cannot establish what is held: a player can own a weapon and tools
together, and `src/game/held.ts:18` currently stores selection locally. The original
suggested guard about “no carried tool” does not distinguish an ordinary weapon swing.
Test identical intents with different flags and mage tool/bolt behavior. Do not turn
this into the deferred HP/path anti-cheat project.

**C6 — P2: Batched consecutive ticks inflate interpolation delay; reset leaves old metrics.
[G4]**

`src/lib/fight-interp.ts:117` compares receipt gaps with 100 ms. Delivering ticks 101
and 102 together after joining at 100 sets the delay to 200 ms. The terminal probe
recorded two gaps (100 and 0 ms); p95 was **100**, not necessarily zero as the report
suggests. `clear()` (`:265`) reset the delay but retained both samples. Confirmation,
prediction and refusal totals also survive reset. The reproduced delay inflation is
real; neither its frequency nor a misleading production p95 has been measured here.

Fix: client lane S–M, account for frame boundaries/number of ticks delivered in a batch
while preserving real network-arrival jitter information. Using tick spacing alone
would always see the server's fixed cadence and conceal genuine transport jitter.
Define metrics as session or lifetime measures and label/reset them consistently on
socket reset; do not reset global metrics whenever one of several rooms changes.
Guard batching, actual uneven arrivals and reconnects.

**C7 — P2: Enemy colliders survive sprite destruction. [G's unverified collider note,
now confirmed]**

`src/game/entities/enemies.ts:434` registers a collider per spawned sprite and discards
the handle. Server lives use that same spawn path (`server-enemies.ts:62`), immediately
disable the body (`:65`), then destroy sprites on death/removal (`:87`, `:123`, `:157`;
`enemies.ts:478`). There is no collider cleanup.

The installed Phaser source settles the reviewer's question without a browser:
`node_modules/phaser/src/gameobjects/GameObject.js:915` destroys the body, while
`physics/arcade/Collider.js:162` requires an explicit collider destroy to unregister it.
A probe using Phaser's actual GameObject and Collider classes showed a destroyed object
still retained by an active collider; one later collider update ran, and explicit
collider destruction removed it. `physics/arcade/World.js:989` continues iterating
registered active colliders. Thus churn retains references and adds per-step work
until scene shutdown. No phone performance magnitude is claimed.

Fix: client lane S, own/destroy each local collider with its sprite, and avoid creating
one for server-owned sprites whose bodies are disabled. Guard repeated life creation,
death and room removal with bounded registered collider counts. This was mentioned
as a question by G, so it is not presented as a finding all four missed.

**C8 — P2: Remembered-credential operations resolve before transaction commit.
[New finding by this verification]**

`src/lib/habitica/remembered.ts:44` resolves IndexedDB operations on request success
(`:49`) and never listens for transaction completion/abort. The same helper backs
credential writes (`:59`) and deletes (`:62`). Consequently `saveRemembered`/`
forgetRemembered` can return true even if the enclosing readwrite transaction aborts;
`src/ui/ConnectGuide.svelte:443` then reports the details forgotten. Closing a database
connection does not make request success equivalent to transaction commit.

A terminal fake-IDB probe delivered request success followed by transaction abort.
`forgetRemembered()` returned true, with neither an abort nor a completion handler
installed. Existing tests use a successful request-shaped fake and pass, so they do
not rule this out. This demonstrates the contract defect, **not** the cause of the
observed post-reload CI flake.

Fix: client lane S, retain the request result but resolve on transaction `oncomplete`,
reject on abort/error and close afterward. Guard put/delete request-success followed
by abort, successful commits and unavailable storage. Keep the UI's explicit refusal
when credentials cannot be cleared.

**C9 — P2: Nested confirms do not own panel shortcuts. [U5, raised from P3]**

`src/ui/ConfirmDialog.svelte:28` stops only Escape. Menu's in-play logout confirm is
local state (`MenuPanel.svelte:64`, `:249`); App's layer flag uses a different
`confirmLogout` (`src/App.svelte:565`). J/C/I/M continue switching panels (`:642`),
unmounting the unanswered confirm. Also, merely adding a logout layer would not
complete the fix: `src/ui/layers.ts:62` does not include it in `appKeys`.

Fix: UI lane S, consume panel shortcuts within the confirm or give nested confirms an
explicit modal keyboard owner honored by App. Preserve Tab, button activation and
Escape cancellation. Guard each panel shortcut during an in-play logout confirm.
