# Verified step-back review after 0.12–0.13

## Summary

The lasting-geography and lamp work holds up. Holds keep their pinned epochs, recovery moves
goods inside one transaction, the previous round's fight, cooldown, inertness and selector
fixes are present, and the settings system and dev/live split are enforced rather than
conventional. No finding needs an architecture round before 0.13.0.

What does need fixing before the release is a cluster of **boundary bugs**, all confirmed
and most reproduced. They sit where asynchronous work meets a lifetime: a transaction that
rolls back, a scene that ends, a world that changes, a Turning that holds play. Concretely:

- a refused camp leaves phantom frontier reach that the next near read trusts (S1);
- a trowel acts before a due backland lapse settles (S2);
- the Turning swallows an authoritative relocation (G1);
- the camp cache crosses worlds (G2);
- the land chip never re-asks after a mutation (G3);
- two UI panels lack read ordering or keyboard ownership (U1, U2).

None of these needs a product decision. The release flow also has no migration rehearsal
step, although live will jump eleven migrations at once (T6). Dev is green only with
retries (T2–T4).

Sol's explanations were accurate. All eleven of its P1/P2 mechanisms survived independent
checking, and S1–S3 and G1–G4 reproduced again here. Corrections are mostly about
**priority and scope**:

- G1 and G2 are real but have narrow windows; I re-rate them P2, though both stay in (A).
- S3 needs a mid-episode world move; I re-rate it P3, a small rider in (A).
- S5's measured gain is larger than reported.
- S6 calls 038–048 "unreleased", but `v0.12.0-alpha.1` tagged 038–047 and staging runs
  them. And **a live deploy freezes them**, so consolidation could only happen before
  0.13.0. The owner has decided to consolidate now (A8) and reset glim-dev.

Opus's U and T findings mostly hold. Corrections:

- T1 cites a file that doesn't exist (`src/lib/crate-picker.ts`).
- T2 misdescribes the bucket step: it does assert the prompt, and the gap is the ordering.
- U's "one dimming rule, no two views can disagree" is contradicted by G5: the lamp art
  helpers use the opposite precedence, though no reachable state shows it today.

Snapshot: `190a9d38` (code identical on `exp/step-back-0.13`, whose only additions are the
four reports). `S`, `G`, `U`, `T` identify findings in the server, game, UI and tooling
reports. Priorities: P1 affects ordinary player use; P2 is a correctness or maintenance
risk; P3 is cleanup. Size S is a focused patch; M is several small patches with boundary
tests; L is staged refactoring. **Confirmed** means the stated mechanism is supported by code

## Verified findings

### Sol: server (S1–S6) and game (G1–G6), checked independently

**S1 — P2 · M: A refused camp publishes reach for a rolled-back hold. Confirmed,
reproduced.**

The ordering is as described:

- `server/internal/api/camps.go:403` takes the hold before checking ground (`:420`),
  communal lamps (`:423`) and oil (`:426`).
- `syncReach` (`server/internal/store/reach.go:53`) sets the process-wide frontier and
  records the transaction as its author.
- `confirmReach` (`:67`) skips repair when the caller is that same transaction (`:71`).
- `nearRead` checks `location.OnGrid` (`open_map.go:121`) before `openEpochs` reaches
  `confirmReach` (via `store/chunks.go:101`).
- Many other `frontier.Inside` readers never confirm, among them `gathering.go:157`,
  `wilds.go:280`, `open_map_paths.go:121` and the fight socket at `presence_fights.go:394`.

My overlay test followed this sequence: a land-blocked camp set returned 409; zero holds
were left in SQL; `frontier.Inside` admitted a chunk three beyond the edge; the next near
read for it returned 200 and only then repaired the cache. The fix direction (transaction-
owned staged reach, refreshed on savepoint/full rollback, confirmed before boundary checks)
is right. As the report says, moving `Hold` later alone does not cover failed commits.

**S2 — P2 · S: The trowel acts before an already-due backland lapse. Confirmed,
reproduced, with a control.**

The mechanism:

- `plant` settles the turning first (`plants.go:154`); `uprootHomePlant` (`:208`) does not.
- `ownLand` trusts the stored `Lantern.Lit` (`gathering.go:58`), which stays true until
  settlement.

The same probe gives opposite outcomes depending on what came first:

- **Raw uproot first:** 200, and the whole plant is in `carried_plants`.
- **After one state read:** 409 `not-your-land`, and nothing is carried. The read settles
  the lapse, so the plant goes to seed storage as the owner ruled.

So the outcome depends on polling order, and the report is right that `opRefreshing`'s
pre-read masks this whole class in the test suite.

Re-rated because it needs a world move (or a replacement household at the same gate)
within one dimming episode. The fix is a few lines: key by home ID with world scope.

**G1 — P2 (was P1) · M: The Turning discards authoritative relocations. Confirmed;
probe reproduced.**

- The Turning's hold sets the same `transitioning` flag that `onRelocate` drops on
  (`WorldScene.ts:683–686`, `:1112`). Nothing is stored for later.
- A ways-home answer goes `link.waysHome` → `refresh({relocate:true})` (`link.ts:2041`) →
  `applyServer` (`session.ts:378`). That updates `session.state.position` and emits the
  relocation, which is then dropped.
- `landed()` releases the hold from the sprite's spot (`world-turning.ts:184–197`), and
  `notePosition` (`WorldScene.ts:982`) writes the departure point back over the
  destination.

Re-rated for frequency. The window is the hold itself: about 2 s of veil, plus
`prepareWilds`, plus at most `LAND_WAIT_MS`. Input is held throughout (`:1045`), so the
request must already be in flight when a Turning begins.

Decision #55 shows Turnings do start during ordinary play (`wickSlack`), and the player
loses the travel they paid for, so this stays in (A). I did not trace how the server
treats the following departure-point report. That changes which side ends up wrong, not
whether the client is wrong.

**G2 — P2 (was P1) · M: The camp cache crosses worlds; naming callbacks outlive the
scene. Confirmed; probe reproduced.**

- `campsKnown` (`camps-state.ts:9`) is a module singleton.
- The controller's shutdown (`camps.ts:75–79`) clears art but not the cache.
- `afterMove` (`src/ui/account-flow.svelte.ts:422`) switches worlds in-page and calls
  `leaveWorld`, which resets only Wilds (`App.svelte:509`).

  (`camps.ts:92–101`).
- Both `beginNaming`s (`camps.ts:330`, `communal-lamps.ts:277`) emit `lampNamingOpen`
  after an await with no scene or link fence.

Re-rated because the wrong camps last one GET round trip after a world move (longer only
when offline), and the server refuses any build they would prompt. The inventory choices
(`InventoryPanel.svelte:368`) are wrong for the same window. Sign-out followed by another
account's sign-in on the same page also inherits the cache.

**G3 — P1 · M: The land chip neither recovers nor invalidates after ordinary land
changes. Confirmed; probe reproduced.**

- `LandHere.update` returns early when the player hasn't stepped and the chunk was already
  asked (`land-here.ts:46`), so a store-version bump never re-asks.
- `refreshLand` swallows failures (`store.ts:551`).
- The mutation paths named in the report never refresh `view.land`:
  - path answers that apply cleanly skip `requestRead` (`ops.ts:160–166`);
  - communal post, lift and relight update only the lamp list (`communal-lamps.ts:320–323`);
  - lot-lantern fill reloads Home only (`homestead-talk.ts:399–405`);
  - camp take-down (`remove`) is missing from the refresh list (`camps.ts:386`).

I keep this at P1. It is deterministic after first-path, first-communal-lamp and
lantern-fill actions, and the chip is the readout players use to judge what will last.
It heals on a chunk crossing, so no server state is wrong.
